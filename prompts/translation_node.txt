You are matching the fields of one kind of record (LEFT) with the fields of
another kind of record (RIGHT). Decide which LEFT fields describe the same
property as which RIGHT fields. You do not convert values. You only decide which
fields correspond.

**INPUT**

The input has two sections.

[LEFT]
One or more source samples, separated by `---EXAMPLE SEPARATOR---`. Each sample
contains:

- [OBJECT]: the record as a JSON object mapping field names to values. Values
  are typed: they may be strings, numbers, or booleans. A field that occurs more
  than once in the record holds an array of values. The values have already been
  cleaned up, so they can differ from the raw text in the document. For example,
  a relative time such as "2 hours ago" may appear as a number of seconds.
- [SOURCE DOCUMENT]: the document the record was extracted from. Content between
  `<!-- TARGET_START -->` and `<!-- TARGET_END -->` marks where the values of the
  record's fields appear in the document. Several marked regions may appear, and
  they may be nested. The markers are not data. Use the document and the markup
  around the markers to understand what each field means and how its value is
  displayed.

[RIGHT]
Zero or more target records, each introduced by `EXAMPLE:` and containing lines
of the form `key = value`. Keys repeat across records while values vary. No
source document is given for these records, so a RIGHT field can only be
understood from its key and its values. Treat the values as the form the LEFT
fields would need to take.

The samples are a sample of each side, not a complete schema. A record may have
fields that the other side does not have.

Field names are hints, not proof. Confirm what a field means from its values,
types, formats, and ranges, and, for LEFT fields, from the context in the source
document.

**THE GOAL**

Return every pair of one LEFT field and one RIGHT field that describe the same
property of the same kind of entity. Return only pairs you can defend. Returning
no pairs is a valid answer.

**HOW TO MATCH**

Two fields match when:

- They describe the same property of the same kind of entity. A shared topic is
  not enough. Two fields about the same entity do not match unless they carry the
  same property.
- The values of one are a representation of the values of the other. Surface
  differences such as units, labels, wrappers, abbreviation, casing, encoding, or
  a trailing time zone designator do not rule out a match.
- A single general rule could turn the LEFT values into the RIGHT form, without
  an external lookup and without guessing individual values.

Consider:

- Meaning, from the field name, the values, and the source document's context.
- Data type, format, and structure.
- Units, prefixes, suffixes, and labels.
- Whether a value is relative, abbreviated, or encoded, and whether the
  information needed to resolve it is available. A relative quantity, such as an
  elapsed time, does not match an absolute one, such as a calendar timestamp,
  unless the input supplies the reference point. If the LEFT record has a field
  that already holds the absolute form, it is the better match.
- Plausible value ranges.

Rules:

- Each LEFT field appears in at most one pair, and each RIGHT field appears in at
  most one pair.
- When several LEFT fields could match one RIGHT field, pair the one that needs
  the least conversion and leave the others unpaired. Do the same in the other
  direction.
- Do not match fields because their primitive types agree, or because of their
  position in the record.
- Do not match a field that holds a different property of the same entity. For
  example, a link to an item is not a link to a discussion about the item, and
  the name of an author is not a link to the author.
- Do not match a field when the correspondence depends on information the input
  does not provide.
- Leave fields unpaired when the other side has no counterpart for them.
- Use field names exactly as they appear in the samples.

**RESPONSE FORMAT**

Respond with valid JSON only. Do not include Markdown, code fences, comments, or
text outside the JSON. Use exactly this structure:

{
  "matches": [
    { "left_field": "<a key from [LEFT]>", "right_field": "<a key from [RIGHT]>" }
  ]
}

- `left_field` must be copied exactly from a key in the [LEFT] objects.
- `right_field` must be copied exactly from a key in the [RIGHT] records.
- If no fields match, return:

{
  "matches": []
}
