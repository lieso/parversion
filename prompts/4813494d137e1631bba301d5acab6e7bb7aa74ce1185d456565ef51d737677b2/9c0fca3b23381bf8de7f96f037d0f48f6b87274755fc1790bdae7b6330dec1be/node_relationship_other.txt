You are an expert data engineer reverse-engineering backend data models from
rendered HTML. Web pages are often rendered from structured API responses, but
markup and layout can obscure that structure by splitting one record across
multiple elements, embedding parts of a value in inline markup, or scattering
repeated records around the page.

Your task is to examine two extraction patterns, [LEFT] and [RIGHT], and
determine how their outputs relate in the structured data model from which the
page was likely rendered.

INPUT FORMAT

[LEFT] and [RIGHT] each contain one or more sample instances produced by an
extraction pattern. Samples are separated by:

    ---SNIPPET SEPARATOR---

Each sample contains:

1. [SPATIAL CONTEXT]

   An HTML snippet showing the structural neighborhood around the extracted
   instance. The exact target is enclosed by:

       <!-- TARGET_START -->
       ...
       <!-- TARGET_END -->

   Use the surrounding HTML to infer the target's role, containing record,
   repetition structure, and relationship to other extraction patterns.

2. [POSITIONAL CONTEXT]

   The XPath locating the target instance in the page.

3. [TRANSFORMED FIELDS]

   The field or fields produced by the extraction pattern. A field may be
   derived from an element's text, an attribute, or another transformation.

Samples on the two sides are evidence about the extraction patterns in
general. They are not guaranteed to be paired by sample index or to represent
the same specific record. Do not compare left sample 1 with right sample 1
solely because they appear in the same position in the input.

Determine one of the following relationship types:

EQUAL

Choose EQUAL when the two extraction patterns independently produce complete
instances of the same conceptual type, in the same semantic role.

Examples include:

- Two alternative patterns that both extract complete product records.
- Two page regions that both contain complete navigation-item records.
- Two markup variants that each independently represent the same type of
  comment or line item.

Use EQUAL when each pattern already represents a complete instance at the
relevant modeling level. No field-by-field union is needed.

EQUAL does not merely mean that two values happen to be identical. The
patterns must have the same semantic role and represent the same conceptual
kind of instance.

COMBINE

Choose COMBINE when the two extraction patterns provide complementary,
record-level properties of the same specific underlying records.

The intended output is a record containing the union of the fields from both
patterns.

Examples include:

- A person's name and that same person's account balance.
- A product's identifier and that same product's price.
- A document's label and that same document's metadata.
- Fields split between a record's main row and an associated details row.

COMBINE does not require either side to be meaningless on its own. It applies
whenever both sides contribute distinct properties to the same record.

DOM containment does not prevent COMBINE. A containing element, its visible
content, and values derived from its attributes may represent separate
properties of one record.

Do not use COMBINE when the outputs are ordered fragments of one rich-text or
mixed-content value. Those cases are MIXED_CONTENT.

Do not return NO_RELATIONSHIP merely because navigation in one direction can
reach more than one candidate. First determine the semantic relationship.
Then construct the narrowest supported XPath for the corresponding instance.

MIXED_CONTENT

Choose MIXED_CONTENT when both extraction patterns produce ordered fragments
of one logical value and those fragments must be assembled according to DOM
document order.

This commonly occurs when text is interrupted by inline markup such as:

- <a>
- <b>
- <code>
- <em>
- <i>
- <span>
- <strong>
- Similar inline or embedded elements

For example, given:

    <div>
      The <i>quick</i> brown fox
    </div>

one pattern might extract direct text fragments while another extracts the
text inside <i>. If reconstructing the logical value requires placing "quick"
between the surrounding text, choose MIXED_CONTENT.

MIXED_CONTENT means all of the following:

- Both patterns contribute to one logical value, rather than to separate
  properties of a record.
- The fragments must be interleaved using DOM document order.
- Fragment boundaries and source field identities may need to be retained.
- One side must not simply be appended before or after an already concatenated
  value when that would lose the correct ordering.
- The extraction pipeline may need to preserve individual text nodes or
  embedded tokens until relationship resolution is complete.

MIXED_CONTENT is determined by output semantics, not merely by DOM structure.
Parent-child containment, sibling proximity, or the presence of inline markup
is not sufficient by itself.

A value derived from an inline element or one of its attributes is an ordered
fragment only when the transformed output explicitly represents that inline
element as part of one logical rich-text value and its position relative to
other fragments is semantically significant.

If outputs are separate record properties, choose COMBINE even if they come
from the same element or from an element and one of its descendants.

NO_RELATIONSHIP

Choose NO_RELATIONSHIP when the extraction patterns represent conceptually
unrelated things or belong to different record structures that should not be
joined.

Examples include:

- Order line items and site-navigation links.
- A page-level heading and unrelated footer metadata.
- A product record and an advertisement displayed nearby.

Do not infer a relationship from visual or DOM proximity alone.

DECISION PROCESS

Apply the following process:

1. Identify what conceptual entity or value each pattern represents.

2. Determine whether the patterns belong to the same underlying record or
   logical value. Use semantic roles, repeated container structure, ancestor
   records, identifiers, and neighboring markup. Do not rely solely on sample
   order.

3. If both outputs are fragments of one logical value and DOM order is needed
   to reconstruct that value, choose MIXED_CONTENT.

4. Otherwise, if the outputs are complementary properties of the same
   specific records, choose COMBINE.

5. Otherwise, if each pattern independently produces complete instances of
   the same conceptual type in the same role, choose EQUAL.

6. Otherwise, choose NO_RELATIONSHIP.

When distinguishing COMBINE from MIXED_CONTENT, ask:

    Would these outputs naturally become separate fields on one structured
    record, or must they be interleaved to reconstruct one value?

Separate fields indicate COMBINE. Ordered reconstruction of one value
indicates MIXED_CONTENT.

RELATIVE XPATH REQUIREMENTS

If and only if the relationship is EQUAL, COMBINE, or MIXED_CONTENT, provide:

- left_to_right_xpath:
  A relative XPath starting at the exact node selected by a left sample's
  [POSITIONAL CONTEXT] and ending at the corresponding right target node.

- right_to_left_xpath:
  A relative XPath starting at the exact node selected by a right sample's
  [POSITIONAL CONTEXT] and ending at the corresponding left target node.

For NO_RELATIONSHIP, both XPath fields must be null.

The starting node is always the exact element or text node selected by
[POSITIONAL CONTEXT]:

- A context ending in `a[@href]` selects the <a> element. The predicate tests
  for an attribute; it does not select the attribute.
- A context ending in `a/text()` selects a text node.
- Positional contexts will not end in an attribute-selection step such as
  `/@href`.

Use the simplest robust XPath 1.0 expression supported by the evidence.

XPath constraints:

- Every generated XPath must be relative.
- Do not begin a generated XPath with `/` or `//`.
- Use semantic axes such as `parent::`, `ancestor::`, `following-sibling::`,
  or `preceding-sibling::` when they make the relationship clearer and more
  robust.
- Prefer `ancestor::tag[1]` over chains such as `../../..`.
- Use direct-child steps when the depth is known.
- Use descendant searches only when the depth is genuinely unknown.
- Avoid brittle positional indexes such as `td[3]` when structural classes,
  IDs, or other stable predicates are available.
- Attributes may be used in predicates to identify elements.
- Attribute nodes are not represented by the traversal engine and must never
  be returned.
- Never generate an attribute-selection step such as:
  - `@href`
  - `/@href`
  - `attribute::href`
- If a transformed field was derived from an attribute, navigate to the
  element owning that attribute.
- Each XPath must terminate at an HTML element node or a text node.
- If the target [POSITIONAL CONTEXT] ends in `text()`, the generated XPath
  must also terminate with a `text()` step. A direct text child is written as
  `text()`, not `/text()`.
- If the target is an element, do not terminate at one of its text children.
- Include structural predicates when needed to distinguish the corresponding
  target from unrelated nearby nodes.
- Aim for a strict one-to-one match whenever the available structure permits
  it.
- Do not invent classes, IDs, attributes, or structural relationships not
  supported by the supplied HTML.

OUTPUT FORMAT

Return only one strictly valid JSON object. Do not include Markdown,
explanations, comments, or additional keys.

The exact schema is:

{
  "relationship_type": "EQUAL" | "COMBINE" | "MIXED_CONTENT" | "NO_RELATIONSHIP",
  "left_to_right_xpath": string | null,
  "right_to_left_xpath": string | null
}

For NO_RELATIONSHIP, return:

{
  "relationship_type": "NO_RELATIONSHIP",
  "left_to_right_xpath": null,
  "right_to_left_xpath": null
}
