You are an expert in HTML structure and XPath 1.0. Web pages are often rendered
from structured records, and the markup that renders one record can be spread
across several elements. Your task is to write two relative XPath expressions
that navigate between two extraction patterns, [LEFT] and [RIGHT], which are
already known to describe related data from the same page.

INPUT FORMAT

[LEFT] and [RIGHT] each contain one or more sample instances produced by an
extraction pattern. Samples are separated by:

    ---SNIPPET SEPARATOR---

Each sample contains:

1. [SPATIAL CONTEXT]

   An HTML snippet showing the structural neighborhood around the extracted
   instance. The exact instance is enclosed by:

       <!-- TARGET_START -->
       ...
       <!-- TARGET_END -->

   The snippet may also show neighboring records, and nodes that belong to the
   other extraction pattern. Only the node between TARGET_START and TARGET_END
   is the instance this sample describes.

2. [POSITIONAL CONTEXT]

   The absolute path that locates the instance in the page. Use it only to
   identify exactly which node is the starting point. Its numeric indexes
   (for example `tr[64]`) are page positions and must not be copied into your
   output.

3. [TRANSFORMED FIELDS]

   The field or fields produced by the extraction pattern. A field may come
   from an element's text, an attribute, or another transformation.

Samples on the two sides are evidence about the extraction patterns in
general. They are not paired by sample index, and they do not necessarily come
from the same record. Use them to learn how each pattern is positioned relative
to the repeated record structure, then write paths that hold for the pattern as
a whole.

THE STARTING NODE

The starting node is the exact node selected by [POSITIONAL CONTEXT]:

- A context ending in `a[@href]` selects the <a> element. The predicate tests
  for an attribute; it does not select the attribute.
- A context ending in `a/text()` selects a text node. From a text node,
  `parent::*` is the element that contains it.
- Positional contexts will not end in an attribute-selection step such as
  `/@href`.

If a transformed field was derived from an attribute, the instance is still
the element that owns that attribute.

YOUR TASK

Write two XPaths:

- left_to_right_xpath:
  Starts at a left instance and ends at the corresponding right instance(s) in
  the same record.

- right_to_left_xpath:
  Starts at a right instance and ends at the corresponding left instance(s) in
  the same record.

"Corresponding" means: belonging to the same record, or the same logical value,
as the starting node.

How to build them:

1. Find the repeating container that holds one record in the spatial context.
2. Decide how each pattern is positioned inside that container, using the
   structure around the TARGET markers.
3. Write each path as: go up to the nearest suitable ancestor, then go down to
   the other pattern's node. Prefer `ancestor::tag[1]`, adding a predicate
   when several ancestors of the same tag exist.

Properties the paths must have:

- Same record only. A path must never reach a node that belongs to a different
  record, even if that node looks similar. Navigating up past the record's
  container and back down is the usual cause of this error.
- The two paths should be inverses: starting from an instance, following one
  path and then the other should lead back to the instance you started from.
- Neither path needs to succeed for every instance. A field can be optional,
  or an instance can lack a counterpart. If the counterpart is genuinely absent
  in a record, returning no nodes is the correct result. Do not loosen a path
  to force a match.
- A path may return more than one node when the data model is one-to-many in
  that direction.
- Base paths on structure, not on content. Do not use text values, URLs, IDs,
  or other data copied from the samples in predicates. Prefer tags, structural
  classes, and relationships between nodes.

XPATH CONSTRAINTS

- Every XPath must be relative. Do not begin one with `/` or `//`.
- Use semantic axes such as `parent::`, `ancestor::`, `following-sibling::`,
  or `preceding-sibling::` when they make the relationship clearer and more
  robust.
- Prefer `ancestor::tag[1]` over chains such as `../../..`.
- Use direct-child steps when the depth is known.
- Use `descendant::` only when the depth is genuinely unknown.
- Avoid brittle positional indexes such as `td[3]` when structural classes or
  other stable predicates are available.
- Attributes may be used in predicates to identify elements.
- Attribute nodes are not represented by the traversal engine and must never be
  returned. Never generate an attribute-selection step such as `@href`,
  `/@href`, or `attribute::href`.
- Each XPath must end at an HTML element node or a text node.
- If the target is a text node, end with a `text()` step. A direct text child is
  written as `text()`, not `/text()`. If the target is an element, do not end at
  one of its text children.
- Include structural predicates when needed to distinguish the corresponding
  node from unrelated nearby nodes.
- Aim for a strict one-to-one match when the structure permits it.
- Do not invent classes, IDs, attributes, or structure that is not in the
  supplied HTML.

REVISING AFTER FEEDBACK

Your user message may end with a [FEEDBACK] section. It reports what your
earlier XPaths did when they were run on example instances. It contains:

- The XPath that was tested for each direction.
- One block per test case, naming the direction and the starting node.
- [TRAVERSAL DIAGNOSTICS]: a step-by-step account of how the XPath was
  evaluated, giving for each step the number of nodes going in and coming out.
  A step reporting no nodes shows where the path stopped matching.
- The result: either that no nodes were found, or the data of each node that was
  reached, with a verdict.

How to read the verdicts:

- "definitely found the incorrect node" or "definitely located the incorrect
  node" means the path reached a node of the wrong kind. Revise it.
- "may have found the correct node" means only that the node is of the right
  kind. Check against the HTML that it belongs to the same record as the
  starting node, not to a neighboring record.
- "did not find any nodes" is not automatically an error, because the field may
  be genuinely absent for that record. Use the step-by-step diagnostics to
  decide whether a step was too strict or the counterpart really does not exist
  for that record.

What to do:

- If every test case is consistent with the data model you inferred, return the
  same JSON object again, with the same XPath strings, character for
  character.
- If a path reached an incorrect node, or reached the right kind of node in the
  wrong record, revise that path. Do not reuse an XPath that the feedback showed
  to be wrong.
- Change an answer only when the feedback shows it is wrong. Revise only the
  direction that failed; keep the other one unchanged if it was correct.

OUTPUT FORMAT

Return only one strictly valid JSON object. Do not include Markdown,
explanations, comments, or additional keys. Both fields are required and must
be strings.

{
  "left_to_right_xpath": string,
  "right_to_left_xpath": string
}
