You are an expert data engineer reconciling extraction patterns drawn from a
single JSON document of unknown origin and unknown quality. Related data in a
JSON document is often nested at different depths or repeated in several
places, and key names may be inconsistent.

You are looking at several sample *entities* extracted from a single document.
An entity is one record of a single type (a comment, a row, a listing, a
category, etc.), reassembled from the fields of one extraction network. Each
sample is a different instance of the same entity type, taken from a different
location in the same document. Your job is to determine whether instances of
this entity stand in a **parent-child relationship to one another** — that is,
whether an instance can be the parent of other instances, as in a threaded
comment tree, nested categories, or a folder structure — and if so, to write
XSLT that finds the parent or the children of an instance.

**INPUT CONTEXT EXPLAINED:**

[ENTITIES] contains several sample instances of the entity, separated by
---SNIPPET SEPARATOR---. Each sample has:

1. [SPATIAL CONTEXT]: a portion of the JSON document surrounding this instance.
   The objects belonging to this instance carry the marker key
   `"__target__": true`. A single instance may be made of several marked
   objects (for example an item and an object nested inside it, such as its
   author or its details). Markers may be nested. The outermost marked object
   of an instance is its *anchor*. Every marked object is part of this one
   instance. Objects without the marker are not part of it: they may be other
   instances of the entity, shown in full. The marker key is added for your
   benefit and is not part of the document's data.

All samples come from the same document, so the instances shown may be related
to one another. Each sample marks a different instance. Do not assume the
samples are listed in any meaningful order.

**DECISION CRITERIA FOR relationship_type:**

- **PARENT_CHILD**: Instances are organised hierarchically. At least some
  instances are the parent of other instances (e.g. a reply to a comment, a
  subcategory within a category, a nested folder). An instance has at most one
  parent and any number of children. The same instance may be both a child of
  one instance and the parent of others.

- **NO_RELATIONSHIP**: Instances are independent of one another. They may be
  items of a flat list or siblings under one key, but no instance contains,
  owns, or is a reply to another.

Evidence for a hierarchy includes: instances physically nested inside another
instance's object (for example under a key whose value holds objects of the
same shape); fields that encode nesting depth; fields that reference another
instance (such as a parent identifier matching another instance's identifier);
and containers that group child instances beneath a parent. Evidence against
one includes: instances that are all items of the same array or siblings under
the same key at the same depth, and repeated instances whose only commonality
is a shared ancestor.

Do not assume a particular domain or hierarchy style — infer it from the
structure shown. A document showing only top-level instances is not evidence
against a hierarchy; if the structure elsewhere shows that nesting is
possible, choose PARENT_CHILD.

**HOW THE TREE IS BUILT:**
The XSLT you write is evaluated over a tree of nodes built from the document,
not over the raw JSON text. Build the tree in your head using these rules:

* An object that holds fields (its scalar keys) is a *data node*. It has no
  name.
* Every key whose value is an object, or an array that contains objects,
  produces two levels in the tree: first a *named node* whose name is that key
  and which holds no fields, and directly beneath it one data node for each
  object (one for an object value, one per object item for an array value).
  A data node therefore never has a data node as its direct child: there is
  always a named node in between.
* Items of the same array are sibling data nodes under one shared named node.
* A data node's fields are only its scalar keys. A field may be tested as an
  attribute of its data node (e.g., `@id`). Keys whose values are objects or
  arrays of objects are not fields. They are the named nodes beneath it.
* Exception: an object whose only key holds an object or an array of objects
  has no fields of its own, so it is treated as the named node itself, with no
  separate data node above it.
* The marker key `__target__` is not a field and does not appear in the tree.

The anchor of an instance is therefore a data node. Starting from it, the
stylesheet must locate the anchors (data nodes) of other instances.

Example. For the document:

    {"nodes": [{"id": 1, "children": [{"id": 2}, {"id": 3}]}]}

the tree is:

    root
    └─ nodes               (named node)
       └─ data node        (id: 1)
          └─ children      (named node)
             ├─ data node  (id: 2)
             └─ data node  (id: 3)

The children of the instance with id 1 are `children/*`. The parent of the
instance with id 2 is `ancestor::children[1]/parent::*`. A top-level instance
has no ancestor named `children`, so that expression locates nothing for it,
as required.

**XSLT:**

**IF AND ONLY IF you choose PARENT_CHILD**, provide two stylesheets:

- `child_to_parent_xslt`: starting from the anchor of a child instance,
  locates the anchor of its parent instance. It must locate at most one node.
- `parent_to_child_xslt`: starting from the anchor of a parent instance,
  locates the anchors of all of its *direct* children (not grandchildren).

Each stylesheet starts from the anchor of an instance and must locate only the
anchors of other instances — never the starting node itself, other marked
objects within an instance, named nodes, or arbitrary containers.

Each stylesheet must handle every structural arrangement shown in the samples
(for example, children nested under one key in some places and under another
elsewhere), combined into a single stylesheet. The two stylesheets are applied
independently of each other, so each must be correct on its own.

Requirements:

* Locate only *direct* relatives: parents, never grandparents; children,
  never further descendants.
* It is fine for a stylesheet to locate nothing from some instances (a
  top-level instance has no parent; a leaf has no children). Make sure it
  locates nothing rather than the wrong node. For example, a top-level
  instance's `parent::*/parent::*` would wrongly select the document root.
* Rely on structure and on key names that identify an instance's role, not on
  brittle positional indexes or on the values of fields, except where the
  hierarchy is expressed by a reference field (see below).

The XSLT engine supports only a narrow subset. Stay within it:

* The stylesheet is an `xsl:stylesheet` in the
  `http://www.w3.org/1999/XSL/Transform` namespace with `version="1.0"`,
  containing exactly **one** `xsl:template` with a `match` attribute.
* Use `match="*"` unless you need to restrict the starting node by a field
  (e.g., `match="*[@parent_id]"`).
* The template body may contain only `xsl:variable` (with `name` and `select`)
  and `xsl:copy-of` (with `select`). The nodes selected by `xsl:copy-of` are
  the result. Do not use literal result elements, `xsl:for-each`,
  `xsl:apply-templates`, `xsl:if`, `xsl:choose`, `xsl:value-of`, or any other
  instruction.
* `select` expressions are XPath 1.0. A step on the `parent::` axis ignores
  any name: `parent::foo` behaves like `parent::*`. To require a particular
  ancestor name, use `ancestor::name[1]`.
* Use `/` for single steps (e.g., `children/*`). Avoid `//` unless the nesting
  depth is genuinely unknown.
* Where the hierarchy is expressed by a reference field instead of nesting,
  bind the reference with `xsl:variable` and compare it in a predicate against
  the matching field of other instances, anchored at a stable common ancestor.
  Prefer nesting-based paths whenever the document shows nesting.

Example stylesheet for the example above (child to parent):

    <xsl:stylesheet version="1.0" xmlns:xsl="http://www.w3.org/1999/XSL/Transform">
      <xsl:template match="*">
        <xsl:copy-of select="ancestor::children[1]/parent::*"/>
      </xsl:template>
    </xsl:stylesheet>

For NO_RELATIONSHIP, set both stylesheet fields to null.

Respond with strictly valid JSON (escape the stylesheets as JSON strings):
