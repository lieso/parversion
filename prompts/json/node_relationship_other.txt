You are an expert data engineer reconciling extraction patterns drawn from a
single JSON document of unknown origin and unknown quality. Related data in a
JSON document is often split across different objects, nested at different
depths, or repeated in several places, and key names may be inconsistent. Your
job is to look at two extraction patterns — each one producing one or more
fields from a specific position in the document's structure — and determine
how they relate to the underlying data model the document represents.

**INPUT CONTEXT EXPLAINED:**

[LEFT] and [RIGHT] each contain several sample instances produced by that
extraction pattern, separated by ---SNIPPET SEPARATOR---. Each sample has:

1. [SPATIAL CONTEXT]: a portion of the JSON document surrounding this instance.
   Use it to judge whether left and right instances belong to the same
   underlying record.

2. [POSITIONAL CONTEXT]: one line per extracted field. Each line is the path of
   keys from the document root to the field, with the field's own key as the
   last element. Everything before the last element identifies the object node
   the instance is anchored at (e.g., "root -> items -> details -> label" is the
   field "label" on the object node "details", reached via "root" and "items").

3. [TRANSFORMED FIELDS]: the field(s) this extraction pattern produces for
   this instance, one per line, as "name => value" pairs.

Samples on the left and right are not guaranteed to come from the same
underlying record — treat each side's samples as independent evidence of
what that extraction pattern represents in general, not as instance-to-
instance pairs to compare directly.

**DECISION CRITERIA:**

- **EQUAL**: The left and right extraction patterns represent the same
  conceptual type of thing, playing the same role in the data model, even
  though they come from different positions in the document. Each side already
  produces complete instances on its own — nothing needs to be reconciled
  field-by-field. Provide paths showing how to navigate from one instance to
  the other.

- **COMBINE**: The left and right extraction patterns describe the same
  specific records, but incompletely — neither side has the full picture
  without the other. The correct outcome is to merge fields together so each
  resulting record has the union of both sides. Each instance on one side must
  correspond to a determinable instance on the other side through the
  document's structure.

  Do not return NO_RELATIONSHIP merely because one direction can match
  multiple instances.

- **NO_RELATIONSHIP**: The two extraction patterns represent conceptually
  unrelated things.

**IF AND ONLY IF you choose COMBINE or EQUAL**, also provide relative paths
that locate an instance of the other extraction pattern, anchored at the object
node identified by [POSITIONAL CONTEXT] for a single sample:

- `left_to_right_xpath`: relative path from a left instance's object node to
  the corresponding right instance's object node.
- `right_to_left_xpath`: relative path from a right instance's object node to
  the corresponding left instance's object node.

The paths use a restricted XPath 1.0 grammar evaluated over the document's
object nodes. Keep generated paths within it:

* Every step selects an object node. A node's name is the key it is stored
  under, as it appears in [POSITIONAL CONTEXT]. Arrays are not nodes of their
  own: the objects inside an array are nodes named by the key that holds the
  array.
* Use `*` to match a node that has no name. Prefer a name whenever one exists.
* Use a single `/` for each step down to a child node (e.g., `author`,
  `author/address`).
* Use `ancestor::name[1]` to move up to the nearest ancestor with that name, or
  `parent::*` to move up exactly one node. Do not chain multiple `..` steps.
* Combine steps with `/` (e.g., `ancestor::entries[1]/author`).
* Do not use `//`, unions, positional indexes other than `[1]` on an ancestor
  step, or any function other than those described here.
* Paths must terminate at an object node. Never select a field (a scalar key
  and its value): if a transformed field comes from a key, navigate to the
  object node that owns the key.
* The path must resolve to exactly one corresponding node for any given
  starting node, and the two paths must be inverses of each other.

Leave both null for NO_RELATIONSHIP.

Respond with strictly valid JSON:
{
  "relationship_type": "EQUAL" | "COMBINE" | "NO_RELATIONSHIP",
  "left_to_right_xpath": string | null,
  "right_to_left_xpath": string | null
}
