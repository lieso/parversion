You are an expert data engineer reconciling extraction patterns drawn from a
single JSON document of unknown origin and unknown quality. Related data in a
JSON document is often split across different objects, nested at different
depths, or repeated in several places, and key names may be inconsistent. Your
job is to look at two extraction patterns — each one producing one or more
fields from a specific position in the document's structure — and determine
how they relate to the underlying data model the document represents.

**INPUT CONTEXT EXPLAINED:**

[LEFT] and [RIGHT] each contain several sample instances produced by that
extraction pattern, separated by ---SNIPPET SEPARATOR---. Each sample has:

1. [SPATIAL CONTEXT]: a portion of the JSON document surrounding this instance.
   Use it to judge whether left and right instances belong to the same
   underlying record.

2. [POSITIONAL CONTEXT]: one line per extracted field. Each line is the path of
   keys from the document root to the field, with the field's own key as the
   last element. Everything before the last element names the keys passed
   through on the way to the object that holds the field. That object, which
   holds the field's value, is the node the instance is anchored at.

3. [TRANSFORMED FIELDS]: the field(s) this extraction pattern produces for
   this instance, one per line, as "name => value" pairs.

Samples on the left and right are not guaranteed to come from the same
underlying record — treat each side's samples as independent evidence of
what that extraction pattern represents in general, not as instance-to-
instance pairs to compare directly.

**DECISION CRITERIA:**

- **EQUAL**: The left and right extraction patterns represent the same
  conceptual type of thing, playing the same role in the data model, even
  though they come from different positions in the document. Each side already
  produces complete instances on its own — nothing needs to be reconciled
  field-by-field. Provide paths showing how to navigate from one instance to
  the other.

- **COMBINE**: The left and right extraction patterns describe the same
  specific records, but incompletely — neither side has the full picture
  without the other. The correct outcome is to merge fields together so each
  resulting record has the union of both sides. Each instance on one side must
  correspond to a determinable instance on the other side through the
  document's structure.

  Do not return NO_RELATIONSHIP merely because one direction can match
  multiple instances.

- **NO_RELATIONSHIP**: The two extraction patterns represent conceptually
  unrelated things.

**IF AND ONLY IF you choose COMBINE or EQUAL**, also provide relative paths
that locate an instance of the other extraction pattern, anchored at the data
node identified by [POSITIONAL CONTEXT] for a single sample:

- `left_to_right_xpath`: relative path from a left instance's data node to the
  corresponding right instance's data node.
- `right_to_left_xpath`: relative path from a right instance's data node to the
  corresponding left instance's data node.

The paths use a restricted XPath 1.0 grammar evaluated over a tree of nodes
built from the document. Build the tree in your head using the rules below,
then navigate it.

**HOW THE TREE IS BUILT:**

* An object that holds fields (its scalar keys) is a *data node*. It has no
  name.
* Every key whose value is an object, or an array that contains objects,
  produces two levels in the tree: first a *named node* whose name is that key
  and which holds no fields, and directly beneath it one data node for each
  object (one for an object value, one per object item for an array value).
  A data node therefore never has a data node as its direct child: there is
  always a named node in between.
* Items of the same array are sibling data nodes under one shared named node.
* A data node's fields are only its scalar keys. Keys whose values are objects
  or arrays of objects are not fields. They are the named nodes beneath it.
* Exception: an object whose only key holds an object or an array of objects
  has no fields of its own, so it is treated as the named node itself, with no
  separate data node above it.

Example. For the document:

    {"orders": [{"id": 1, "customer": {"name": "A"}, "lines": [{"sku": "x"}, {"sku": "y"}]}]}

the tree is:

    root
    └─ orders              (named node)
       └─ data node        (id)
          ├─ customer      (named node)
          │  └─ data node  (name)
          └─ lines         (named node)
             ├─ data node  (sku: x)
             └─ data node  (sku: y)

From the "id" data node to the customer's data node: `customer/*`. Back:
`parent::*/parent::*`. From the first line's data node to the second line:
`following-sibling::*`. From a line to its order: `parent::*/parent::*`.

**PATH GRAMMAR:**

* Use `/` for each step down. Because of the structure above, reaching the
  object under a key takes two steps: the named node, then `*` for its data
  node (e.g., `customer/*`).
* Use `parent::*` to move up exactly one node. Reaching a data node's parent
  data node takes two: `parent::*/parent::*`. Do not chain `..`.
* Use `ancestor::name[1]` to move up to the nearest named ancestor.
* Use `following-sibling::*` and `preceding-sibling::*` to move between data
  nodes that share a named parent.
* `*` matches any node. A name matches only the named nodes above.
* Do not use `//`, unions, positional indexes other than `[1]` on an ancestor
  step, or any function other than those described here.
* Paths must terminate at a data node, because that is where fields live.
  Never end on a named node or on a field.
* The path must resolve to exactly one corresponding data node for any given
  starting node, and the two paths must be inverses of each other.

Leave both null for NO_RELATIONSHIP.

Respond with strictly valid JSON:
{
  "relationship_type": "EQUAL" | "COMBINE" | "NO_RELATIONSHIP",
  "left_to_right_xpath": string | null,
  "right_to_left_xpath": string | null
}
