You are an expert data engineer reverse-engineering backend data models from rendered HTML document fragments.

Your task is to analyze multiple examples of extracted data points and determine how many
distinct semantic entities they represent, and which extracted fields belong to each. You
are determining one or more grouping keys (network names) for the final JSON schema
representation — usually one, but sometimes more if the examples mix fields from more than one kind of object.

### INPUT CONTEXT EXPLAINED:
You will be provided with a payload containing multiple **EXAMPLES** separated by `---SNIPPET SEPARATOR---`. All examples come from the same structural location on the page (the same repeating DOM pattern), but the fields extracted from that location may belong to one entity or to more than one, depending on the page. Each example contains three parts:

1. [SPATIAL CONTEXT]: A zoomed-in HTML fragment showing the target node, its siblings, and its parent wrappers. Use this to understand the structural boundaries of the entity instance.
2. [POSITIONAL CONTEXT]: The exact DOM path identifying a particular node. **Crucially, the entity or entities we are naming are represented by everything nested UNDER this node.** Treat this path as the root of the subtree for that instance.
3. [TRANSFORMED NODES]: The specific data points (both HTML attributes and text nodes) extracted during a previous pipeline step, shown one per line as:

       SOURCE => KEY (value = VALUE)

   SOURCE is the raw HTML attribute or text node the value came from, shown only for context.
   KEY is the field's name in the final data model — this is the identifier you must use everywhere below when grouping keys into entities. All of these values appear somewhere within the DOM subtree identified by the Positional Context.

### INSTRUCTIONS:
1. **Determine distinct entities**: Examine the field keys listed under [TRANSFORMED NODES]
   across all examples. Most of the time, all keys belong to a single entity type. Only
   split into multiple entities when the keys clearly represent semantically distinct
   objects (not just different fields of the same object) — for example, a key set
   describing a "product" versus a separate key set describing that product's "seller".

   **Exception — repeated keys**: If the same key appears more than once within a single
   example (i.e. the same KEY has multiple different values listed under [TRANSFORMED NODES] for 
   that example), this means the example actually spans multiple real-world instances
   rather than describing one coherent object. In that case, do not group that key with
   any other key — give every key present in that example its own single-key entity
   instead of attempting to merge them.
2. **Group the keys**: For each distinct entity you identify, list exactly which field
   keys (verbatim, as they appear in [TRANSFORMED NODES]) belong to it. Every key must
   be assigned to exactly one entity group.
3. **Name and describe each entity**: Create a semantically accurate `snake_case` name
   and a concise API-documentation-style description for each group.

Note: the key groupings you choose will be applied uniformly to every instance of this
structural pattern across the entire document, not just the examples shown here — so base
your grouping on what the keys semantically represent, not on incidental gaps or quirks in these particular examples.

### RESPONSE FORMAT:
Respond with strictly valid JSON matching this schema:
{
  "entities": [
    {
      "keys": ["string", "..."],
      "name": "string",
      "description": "string"
    }
  ]
}
